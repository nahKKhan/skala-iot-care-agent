# RAG와 점검 품질 검증

## 검색 자료와 흐름

현재 RAG 자료는 Shelly 공식 페이지6개에서 정리한 한국어 요약8개·24문단과
프로젝트 가상 복구 정책2개·6문단이다. 원문 전체 번역이나 제조사 공인 번역은 아니다.
원문과 적용 범위는 [공식 매뉴얼 적용 내역](official_manuals.md)을 참고한다.

- data/iot_manuals/: 공식 문서 기반 한국어 요약.
- data/iot_policies/: 명령 접수와 복구 검증, 반복 실행 방지 등 프로젝트 정책.
- agent/manual_search.py: 한국어 단어·문자2-gram BM25 문단 검색. 임베딩·벡터 DB는 사용하지 않는다.

검색 자료에 source_type, publisher, source_url, source_title, source_section, retrieved_at,
applicable_models, version을 보관한다. 원문 절·확인 날짜와 로컬 요약 버전은 서로 다른 정보다.

문서를 읽고 ## 제목으로 나눈 뒤 질문·관측 증상에 맞는 문단을 검색한다.
기본 최대3개, 문서당1개 문단을 반환한다. 모델과 전원 방식의 적용 범위도 확인한다.
다른 모델에 Shelly 문서를 자동 적용하지 않는다. 일반 질문에서는 명시된 전원 방식에 맞는 문단을 우선 대상으로 삼는다.
검색 점수는 순위용 수치이며 고장 원인 확률이나 신뢰도 백분율이 아니다.

흐름: 대상·상태 확인 → 로그·문서·이력 조회 → LLM 설명·후보 선택 → 코드 검수 →
통과하면 기록, 미달이면 최대1회 재작성, 재차 미달·모델 오류이면 규칙 안내.

## 모델과 코드의 역할

- 상태 분류·복구 허용·복구 결과는 코드가 판정한다.
- LLM은 검색된 메타데이터의 원인 후보를 최대2개 선택하고 관측 사실을 설명한다.
- 문서별 후보와 확인 안내는 프로젝트가 문서에 근거해 구성한 해석이다. 제조사가 현재 가상 장치 원인을 판단한 결과가 아니다.
- 요청별 JSON Schema에 허용 출처 ID·후보 ID·조치 문구·확인 한계를 제한한다.
- 코드에서 출처 존재, 후보와 출처 관계, 허용 조치, 수치, 일부 근거 없는 단정을 검사한다.
- 형식·정책 검수는 문장 의미 전체의 근거 일치나 실제 원인의 정확성을 보장하지 않는다.
- 숨겨진 복구 결과·평가 정답을 생성 입력에 전달하지 않는다.

제조사 문서 요약과 프로젝트 복구 정책의 구분을 모델 입력과 화면에도 전달한다.
restart_collection은 가상 수집기를 재시작하며 실제 Shelly Reboot를 호출하지 않는다.
보고 조건은 USB300초·배터리7200초를 참고한다. 여유60초·배터리20% 기준은 프로젝트 정책이다.

## 이력과 갱신

진단 이력에는 검색 당시 문단 본문·원문 URL·출처 유형·요약 버전·색인 버전을 함께 저장한다.
문서 수정 후 MCP/백엔드를 재시작해야 새 색인이 적용된다.
매 질문마다 웹을 검색하는 방식이나 공식 문서 자동 동기화는 구현하지 않았다.

## 문서 추가·수정

공식 문서 요약은 기존 data/iot_manuals/ 파일의 JSON 메타데이터를 참고한다.
source_type은 manufacturer_summary로 지정하고 공식 원문 HTTPS URL·제목·절·확인 날짜·적용 모델을 기록한다.
현재 공식 출처 호스트는 kb.shelly.cloud와 shelly-api-docs.shelly.cloud로 제한한다.
새 제조사를 도입하려면 검증 후 색인과 화면의 출처 호스트 허용 목록을 함께 수정한다.

프로젝트 정책은 data/iot_policies/에 두고 source_type을 project_policy로 지정한다.
제조사 URL을 정책의 근거로 꾸미지 않는다.
문서 ID와 후보 ID는 중복되지 않게 하고 ## 제목으로 검색 문단을 나눈다.
section_power_sources로 문단 번호별 usb/battery 적용 범위를 지정할 수 있다.

후보 메타데이터는 문서 공통 내용이며 해당 문서의 검색 문단과 함께 전달된다.
새 증상 유형을 추가하면 분류 규칙·적용 문서·평가 사례를 함께 수정한다.

## 재현 가능한 평가

모델 호출 없이 확인:

    .venv/bin/python scripts/evaluate_iot.py --backend rules --output doc/evaluation_shelly_rules_new.json

실제 로컬 모델의 새 응답을 평가하려면:

    .venv/bin/python scripts/evaluate_iot.py --backend ollama --model qwen3.5:2b --output doc/evaluation_shelly_ollama_new.json

평가기는 임시 DB와 독립 MCP를 사용한다. 과거 평가 파일을 덮어쓰지 않도록 새 파일명을 사용한다.
현재 장치 관측에 과거3배 규칙을 적용한 기준선은 실제 변경 전 실행과 동일한 조건의 비교 실험이 아니다.
실제 모델 답변 품질은 사용할 모델로 다시 평가한다. manual_review의 null은 미검토를 뜻한다.

[공식 문서 교체 후 규칙 평가](evaluation_shelly_rules.md) · [교체 이전 모델 평가](evaluation_ollama.md)

## 공식 매뉴얼 적용 후 실제 모델 평가

2026-10-22 OpenAI gpt-4o로 고정12개 질문을 재평가했다.
실제 모델 호출9건은 모두 코드 검수를 통과했지만, 내용 검토에서 조치 순서·인과관계 단정·절전 표현 문제가 남았다.
자동 검수 지표와 의미 검토를 분리한 [실제 모델 재평가 보고서](model_reevaluation_20261022.md)를 참고한다.
재현 시 --backend openai를 사용할 수 있으며 실제 API 사용료가 발생한다.


## 실제 평가 후 보완한 검수

- 배터리 부족과 연결 불가의 동시 관측 설명, 정상 보고 대기 설명은 required_explanation으로 전달한다.
- 해당 설명을 요청 JSON Schema enum과 코드 검수에도 적용해 인과관계·실제 절전을 확정하지 않도록 한다.
- 일반 설명의 일부 인과 표현을 거부하고 원인 후보는 별도 미확정 목록에서만 선택한다.
- 수집기 재시작 안내를 선택하면 상태 재조회 안내가 그 앞에 있어야 한다. 중복 조치도 거부한다.
- 복합 판단 요청을 단순 상태 조회보다 진단에 우선 분기한다.
- 이는 응용 프로그램의 출력 제약 강화이며 모델 추가 학습이 아니다.

같은 질문12개·공식 문서·장치 데이터의 보완 후 실제 gpt-4o 실행에서 기대 분류·기본 안내12/12,
검색 포함12/12, 모델 호출10개 코드 검수10/10을 확인했다.
소규모 고정 사례의 결과이며 새 질문의 정확도를 보장하지 않는다.
